# Offline reference for the native Gear preview

This packet consists of [synthetic_preview_reference.py](synthetic_preview_reference.py) and its checked [synthetic_preview_vectors.json](synthetic_preview_vectors.json). All fixture numbers are **synthetic**, explicitly supplied by the script. They are not Maurice's `422`, `20`, or actual equipped DPS. The script executes only handwritten Python; no extracted game code is imported or run. It neither opens the game nor writes its installed files or Deviant Forge.

## Source-bound algorithm

Copied client methods and original-archive hashes are recorded in [gear_ui_capture/manifest.json](gear_ui_capture/manifest.json). The precise dataflow is:

1. `ItemDataTools.get_player_replace_affix_list` in `item_data_tools_capture/ItemDataTools.pyc` `[31190,31890)` negates each held-weapon affix in its native source bucket, sums the selected weapon's affix IDs across source buckets, and calls the client property-formula preview with those two arguments. It passes the selected affix sum as `SOURCE_TYPE_GUN_CORE` (13). The older held affixes retain their original buckets. This is not a `new weapon Attack + current Basic Attack` operation.
2. `CompPropertyFormulaClient.get_preview_ability_changes_client` in copied `dcs_extend/component/CompPropertyFormula.pyc` `[28958,30356)` separates source types in `INIT_SOURCE_TYPE_LIST` from `other`, converts the negative affixes into absolute/rate/independent/set changes, **copies** the holder's four change dictionaries, and adds the negative changes. The copied `attr_const.pyc` `[11400,11418)` includes `SOURCE_TYPE_EQUIP` (3) in init; `SOURCE_TYPE_GUN_CORE` (13) is outside it.
3. `CompPropertyFormulaClient.get_preview_ability_infos_by_affix_infos` `[25190,26888)` converts the selected affixes, combines them with the copied holder changes, calculates each affected property, and adjusts it. `AffixUtils.calc_preview_attr_changed_values` `[19153,19855)` maps prototype types to absolute, rate, independent, or set channels. The native `D0100` prototype is `D01/attack`, effect range 1, type 1 (absolute); `D0101` is `D01/attack`, effect range 1, type 2 (rate), in `native_attack_affix_typed_inputs.json`. `AffixUtils.add_effect_all_ability_change` `[13381,14241)` binds those type codes to absolute and rate changes. The script implements only these two affix IDs for weapon fixtures; unknown IDs are rejected.
4. For a property with no set override and no independent rate list, `CompPropertyFormulaBase._calc_attr_by_base_formula` `[7096,7200)` evaluates `(c_init + c_abs) × (1 + c_rate)`. A present set override wins first, including `0`; a nonempty independent list instead calls `_calc_by_rate_addition_type` on `c_init + c_abs` and bypasses the ordinary `c_rate` branch. `_calc_attr_init_val` `[6794,6868)` likewise uses independent init rates **or** `init_abs × (1 + init_rate)`.
5. `_calc_by_rate_addition_type` `[13860,14506)` uses native `calc_type` and `val_type`. For add mode (1), absolute values become `x∏(1+rᵢ)`, while rate values become `(1+x)∏(1+rᵢ)−1`. For minus mode (2), absolute values become `x∏(1−rᵢ)`, while rate values become `1−(1−x)∏(1−rᵢ)`. The script checks these as helper-level cases; it does **not** claim an Attack affix enters the independent-rate channel.
6. `CompPropertyFormulaClient._adjust_attr_val` `[32941,33189)` calls `AffixUtils.adjust_attr_val` `[30004,30500)`: optional linked-maximum restriction, then native min/max clamp, `round(...,6)`, and `int(round(...))` for absolute attributes or `round(...,3)` for rate attributes. Native `attack/D01` has initial `0`, min `0`, max `130000`, absolute `val_type=1` in `native_attack_affix_typed_inputs.json`. Gear's `UIEquipmentData.get_player_weapon_armor_info` `[200591,201451)` applies `int(round(...))` to the result for its summary display.

The non-init preview wrapper at `[26458,26556)` uses a *truthiness* check when choosing a selected set value versus the holder's existing set. Accordingly, a synthetic selected set of `0` falls back to an existing set of `30`, even though `_calc_attr_by_base_formula` itself accepts `0` as a valid override. The reference tests both layers separately; it does not assert that a real weapon has a zero-valued set affix.

Attack absolute rounding gives `10.5→10`, `11.5→12`, clamps `−4→0` and `130000.9→130000`.

## Limits for Forge

The source proves the pure client preview ordering, channel arithmetic, and final adjustment. The handwritten fixture does not reproduce the entire native affix converter for arbitrary effect ranges or independent attributes. It does not know Maurice's held/selected item IDs, affix values, holder change dictionaries, snapshot overrides, or the server's authoritative `holder.attack` producer. The implementation of `ClientAvatar.get_weapon_item_data_by_item_id` that supplies the live cached `all_calc_affix_add` was not present in the copied `ClientAvatar` and `AvatarEntityBase` method bodies. Therefore no valid character-specific equation or DPS result can be derived by fitting `422` and `20`.
